title: Add a machine
description: Link up a machine with one command and approve it in xixo. The folders it shares join the catalog by themselves.
---

This guide links up a machine, such as a home server or a desktop. The folders it shares join the
catalog by themselves. The machine runs xixo link, which dials out to xixo, so the machine opens no
port. See
[machines and xixo link](/concepts/resources/#machines-and-xixo-link) for how it works.

## Requirements

- An administrator's sign-in. Only an administrator sees a machine asking to link up and approves
  it.
- A route from the machine to xixo and to masks.
- On Linux: x86_64 or ARM64, systemd, `curl`, and `sudo` or a root shell.
- On macOS: Apple silicon or Intel. The command uses no `sudo`.

Run the command as the account that owns the folders. xixo link runs as that account and reads
only what it can read.

## Link up a machine

1. On **Resources**, choose the **Link up a machine** tile.
2. Check the system. The dialog shows the command for the system your browser runs on. Choose
   **macOS** or **Linux** to change it.
3. Check the folders. On macOS the command shares `~/Documents` and `~/Desktop`. On Linux it shares
   no folders. To change them, choose **Change** and type the folders, separated by spaces. End a
   folder with `:rw`, such as `/srv/inbox:rw`, to let xixo write into it.
4. Choose **Copy**.
5. Paste the command into a terminal on the machine and run it:

   ```sh
   curl -fsSL https://xixo.example.com/link.sh | sh -s -- ~/Documents ~/Desktop
   ```

6. Wait for the step that asks xixo to approve the machine. It prints a link and a code:

   ```text
   4. Asking xixo to approve this machine.
      Open this link to approve this machine:

        https://xixo.example.com/link/WDJB-MJHT

      Check that the page shows the code WDJB-MJHT, then choose Approve.
      This command waits until you do. The request runs out in 10 minutes.
   ```

7. [Approve the machine](#approve-the-machine). The command waits until you do, then starts xixo
   link and prints a summary, as in [check on a machine](#check-on-a-machine).

The command numbers its steps and prints each one before it starts. When `sudo` needs a password,
the line before it says why.

Each folder must exist, and cannot hold a quotation mark, an apostrophe, a backslash, a colon, or a
control character. Otherwise the command stops before it links up. On Debian or Ubuntu the command
also installs the programs that read PDFs, images, audio, video, and office documents. See
[installing](https://github.com/xixo/xixo/tree/main/link#installing) in the xixo link README for
every step it takes.

When the server holds no builds of xixo link, the dialog says so and shows no command. The server
image puts them in the folder `XIXO_LINK_DIR` names.

### Folders a Mac guards

macOS guards `~/Documents`, `~/Desktop`, `~/Downloads`, iCloud Drive, and removable and network
volumes. Until you grant access, the machine's card shows a warning that macOS has not let xixo
link read the folder. When a shared folder needs access, the command opens the Finder and the
settings for you.

1. Open **System Settings**, then **Privacy & Security**, then **Full Disk Access**.
2. Drag `xixo-link` from the Finder window into the list.
3. Turn on its switch.

The command lists these steps last, with the exact path to add. xixo link checks every 15 seconds
and starts reading the folder by itself. Running the link-up command again keeps the access and
says so. Only a xixo link too old to update itself is replaced, and then the command lists the
steps again. See
[xixo link on macOS](https://github.com/xixo/xixo/tree/main/link#macos) for more.

## Approve the machine

A machine asking to link up shows in the **Link up a machine** dialog at once. With the dialog
closed, a line above the machine cards says so, such as "studio is asking to link up."

1. Choose **Review**, or open the link the command printed. The link opens a page titled with the
   machine's name, such as **Approve studio**, with what the machine says about itself.
2. Check that the code matches the code the command printed on the machine.
3. Read what xixo plans to do with the machine, one switch per line, such as "Catalog Documents.
   Read and write Desktop." and "Use the Ollama already running on it." Turn off a line you do not
   want. A line the machine cannot do stays off and says why.
4. Choose **Approve**. Choose **Deny** for a machine you do not know.

:::caution
Approve a machine only when it shows the same code. Anyone who can reach xixo can ask to link up a
machine, and the code is how you know the request came from the machine in front of you.
:::

xixo adds the machine to **Resources**, and you become its first operator. Its name and its key
are the first part of its hostname, such as `studio`. The key is `studio-2` when `studio` is
taken. Once it connects, its card shows **online** beside its name.

While it waits, the command says once a minute how long the request has left. A request runs out
after ten minutes, and the command prints "Error: the request ran out before anyone approved it.
Run the command again." A denied machine prints "Error: an administrator denied this machine in
xixo. Run the command again to ask again."

## Check on a machine

The link-up command ends with a summary. `xixo-link status` prints the same one at any time, with
no `sudo`:

```text
media is linked up with https://xixo.example.com.

  In xixo    https://xixo.example.com/settings/resources/42
  Version    0.5.0
  Service    running
  Updates    automatic
  Folders    /srv/media  read only
             /srv/inbox  read and write

To check on xixo link:
  systemctl status xixo-link
  journalctl -u xixo-link -f
```

**In xixo** is the address of the machine's card. On a Mac the last two lines show the launch agent
and its log. `xixo-link help` lists the other commands.

## What xixo does with a machine

xixo may do everything with the folders a machine shares. It browses and searches them, fetches
whole files for downloads and previews, runs the machine's readers, and writes into a folder the
machine shares writable.

The machine decides which folders are writable. End a folder with `:rw` in the link-up command, such
as `/srv/inbox:rw`. Any other folder is read only. The machine's card lists each folder it shares,
marked **Read and write** or **Read only**. To change a folder, run the link-up command on the
machine again with the new list.

The machine's card shows the plan xixo made from the machine's description, as switches an
administrator can turn off:

- **Catalog** the folders it shares.
- **Extract** text from documents, and from files other machines lend it. Off, the machine reads
  only its own files.
- **Use** or **run** models. On, xixo attaches the model server it found on the machine by itself.

A change takes effect at once, without touching the machine. xixo plans again each time the machine
connects, so a reader you install or a model server you start shows up on its own. See [what xixo
does with a machine](/concepts/resources/#what-xixo-does-with-a-machine).

The machine's own config can keep its files' bytes on the machine with `lend`. Then the card says
"Its own config holds back whole files". See
[tools a machine offers](/concepts/resources/#tools-a-machine-offers).

## Folders it shares

Each folder a machine shares joins the catalog by itself. There is nothing to attach.

- When the machine connects, xixo adds a folder resource for each folder it shares, such as
  `media-documents`, named **Documents on media**. On **This server** the key is the folder's name
  alone, such as `files`. When the key is taken, xixo adds a number, such as `media-documents-2`.
- A new folder syncs at once, then every hour. In between, xixo link tells xixo which files changed,
  and xixo looks at them within seconds. Any folder synced once follows these changes, with or
  without a schedule.
- A sync where nothing changed reads no file. xixo link lists each file's size and times, and xixo
  compares them with what it holds. xixo link remembers the SHA-256 of each file of 1 MB or more,
  so a large film is read once and not again until it changes.
- A folder someone already attached is used as it is, and never added twice.
- When the machine stops sharing a folder, xixo puts the folder away. Its items stay in the catalog.
  When the machine shares the folder again, xixo puts it back.
- A folder you put away yourself stays put away.

The machine's card lists each folder it shares, with its items, its state, and whether it is
**Read and write** or **Read only**. Syncing while the machine is not connected leaves the folder
**offline** until xixo link is back.

A full sync that finds nothing in a folder where it found files before marks nothing gone, since an
unmounted disk looks the same as an emptied folder. Its items stay until a sync finds files again.

### Who sees the folders

A folder a machine shares starts out held for the machine's operators. Its row shows **only its
operators**.

- Only the people listed under **Who operates it** see the folder and the items it holds. You
  become the first operator when you approve the machine.
- Anyone else, administrators included, does not see the folder or its items. To let someone see
  them, add them to **Who operates it**. See [rename a machine](#rename-a-machine).
- To let everyone here see a folder, open the menu on its row and choose **Show to everyone**. Only
  an administrator who operates the machine can do this. **Keep for its operators** takes it back.

When you are the only person in xixo, you see every folder your machines share.

## Run models on a machine

When a machine has an NVIDIA GPU with a driver and at least 4 GB of memory, or an Apple chip with
at least 16 GB, and no model server already runs on it, the plan's **Models** line reads "Run
models on its NVIDIA GeForce GTX 1070, 8 GB." With that line on, xixo link installs Ollama on the
machine by itself and keeps it running:

1. xixo link downloads the Ollama build pinned in its own source from where Ollama publishes it,
   checks the SHA-256 it was built with, and unpacks it into a folder for that version.
2. It starts Ollama on its own port, so a copy you installed by hand keeps port 11434, and waits
   for it to answer.
3. It pulls the models the machine's memory allows: `qwen3:8b`, `gemma3:4b`, and
   `nomic-embed-text` on an 8 GB card, and larger ones with more memory. The card shows each pull's
   progress, such as "Ollama 0.40.6 is running, pulling qwen3:8b 40%".
4. xixo attaches it as **Ollama on** the machine's name, with a model named for each role, and makes
   it the default for inference when there is no other.

On Linux the part runs as a service of its own, `xixo-link-part@models`, as the system user
`xixo-link-part`, with the GPU devices allowed and no view of the shared folders or home folders. On a Mac
it runs as a child of xixo link, as you. A version that fails its health check is rolled back to
the one before it, and the card says so.

Turning the **Models** line off stops Ollama. Its models stay on disk under
`/var/lib/xixo-link-part/models` on Linux. The machine's own configuration can keep the part off
with `parts` in `/etc/xixo-link/config.json`, as the
[xixo link README](https://github.com/xixo/xixo/tree/main/link#what-xixo-may-do) describes.

## A model server it found

xixo link looks for Ollama and LM Studio on the machine. When the plan's **Models** line is on,
xixo attaches the model server through the machine as soon as the machine connects, named such as
**Ollama on studio**, and makes it the default for inference when there is no other. Nothing
reaches the model server over the network: xixo link on the machine passes each request to it at
`127.0.0.1`.

1. Open the menu on the new row, choose **Change**, and name a model for each role.
2. To stop using it, turn the **Models** line off on the machine's card, or put the resource away.

A laptop sleeps, and its model server goes with it. A file whose summary needs that model server
waits, and its pass says "Waiting for" the machine "to come online". When the machine links up
again, xixo starts the waiting files, at most 50 queued at a time. A model server that is not running,
busy, or out of reach is tried three times, and then the file waits for the next check, ten
minutes later. After twelve such waits the pass fails and says why. A model the server does not
have, or a request it refuses, fails at once.

## Link a machine over SSH

After the first machine, link the rest from your own computer. Nothing needs approving, since
you are signed in, and the machine never shows a code.

1. Install xixo link on your computer with the link-up command, or download the build for it from
   `https://xixo.example.com/link/download/xixo-link-darwin-arm64` and put it on your `PATH`.
2. Sign in once:

   ```sh
   xixo-link login --xixo https://xixo.example.com
   ```

   It prints a link and a code. Open the link, check the code, and approve. The sign-in is kept
   in `~/.config/xixo-link/logins.json`, and masks lists it where you can revoke it.

3. Link up each machine, as `ssh` knows it, with the folders it shares:

   ```sh
   xixo-link add media ~/Documents ~/Desktop-Backup:rw
   xixo-link add old-mbp old-linux-1 old-linux-2
   ```

   The command copies xixo link over your own `ssh`, reads what the machine is, adds it to xixo
   under your name, and prints the plan. On Linux, `sudo` on the machine asks for its password,
   so run the command in a terminal. Then it enrolls the machine and starts xixo link. Pass
   `--off models` to leave a line of the plan off, and `--user NAME` when the folders belong to
   another account on the machine.

4. The machine's card fills in on **Resources** once it connects. Anything you want off, switch
   off there.

Running `xixo-link add` on a machine that is already linked installs the new build and keeps its
place in xixo: the same card, name, and operators. `xixo-link remove media` uninstalls xixo link there and puts the machine away. See
[linking over ssh](https://github.com/xixo/xixo/tree/main/link#linking-over-ssh) for each step.

## Find machines on a tailnet

When xixo reaches a [tailnet](/guides/tailnet/), **Not linked yet** under the machine cards lists
the online machines on it that are not linked up.

- Choose **Link up** beside one to open the **Link up a machine** dialog.
- When a machine runs Ollama or LM Studio, the row says so, such as "Found Ollama". Choose **Add**
  to attach the model server through the tailnet.

## Change the folders

The folders live in the machine's own config, so xixo cannot widen them.

1. Run the link-up command on the machine again, with the new folders.

The machine prints "Already linked up as" followed by its name, and keeps its link and its
approval. Run with no folders, the command keeps the folders it has.

To change them by hand on Linux:

1. In `/etc/xixo-link/config.json`, change the `folders` list. A read-only folder is a path, such as
   `"/srv/media"`. A writable folder is `{"path": "/srv/inbox", "writable": true}`.
2. In `/etc/systemd/system/xixo-link.service`, change the `BindReadOnlyPaths=` line, where each
   folder is written as `"-/srv/media"`. A writable folder goes on the `BindPaths=` line.
3. Run `sudo systemctl daemon-reload`.
4. Run `sudo systemctl restart xixo-link`.

A folder in the config but not in the service is missing for xixo link.

## Give xixo link more memory

The service may use 2 GB of memory. To give it more for large office documents or video:

1. Run `sudo systemctl edit xixo-link` on the machine.
2. Add these lines:

   ```ini
   [Service]
   MemoryMax=4G
   ```

The setting lives in a drop-in file, so running the link-up command again keeps it.

## Keep xixo link up to date

xixo updates xixo link on each machine to the release the server ships, and the card says "updating
to" and the version. A release holds the binary, the systemd units on Linux, the launch agent on
macOS, and the list of programs that read files, so a change to any of them reaches every machine.
Each machine checks that xixo's CI signed the release, and refuses one older than it has run, so
the server cannot install anything else. When a new release does not connect within three minutes,
xixo link goes back to the one before it, and tries again after six hours.

A release reaches the machines in steps. The server runs it first. Once the server has been healthy
for 15 minutes, one machine per platform updates, and the rest follow once that machine has stayed
connected for 30 minutes. **Settings > Updates** shows where the rollout is and where each machine
stands, and an administrator can update a machine now, choose the machine that goes first, pause
one machine or all of them, and roll a machine back to the release it ran before.

- To hold a machine at the release it runs, turn off **Update xixo link automatically** on its
  card, or **Pause** it on **Settings > Updates**. Turn it on again to update at once.
- A Linux machine linked up before xixo link installed releases as root takes the first release
  only through the [link-up command](#link-up-a-machine). Run it once more. It keeps the link, and
  every release after that arrives by itself.

xixo link beside the server updates with its image. See
[updates](https://github.com/xixo/xixo/tree/main/link#updates) in the xixo link README.

## Files a machine cannot read

A file whose program the machine lacks, such as a PDF on a machine without poppler, waits, and the
card counts the files waiting. Do one of these:

- Install the programs on the machine, then run the link-up command again, which restarts xixo
  link.
- Leave lending on. A machine lends its files unless its config sets `lend` to false, and then a
  connected machine whose plan extracts text reads a copy. A file larger than 4 GB is never lent,
  so a large film waits until its own machine has ffmpeg.

A file on a machine that is offline waits for the machine to come back. A file on a machine that is
too busy to take it, or that does not answer within 30 minutes, waits, and xixo asks again at the
next check. When xixo stops waiting, it tells xixo link to stop that extraction, so the machine is
free for the next file. Extractions wait in their own queue on the machine, so a long one never holds
up a sync.

## Rename a machine

1. Open the menu on the machine's card and choose **Change**.
2. Edit the name, or **Who operates it**, the masks subjects whose tokens may use the machine's
   tools, one per line. The operators are also the people who see the folders it shares, unless an
   administrator shows a folder to everyone. A machine that holds folders for its operators needs at
   least one.

The key stays the same.

## Remove a machine

1. Open the menu on each model server reached through the machine, and choose **Put away**.
2. Open the menu on the machine's card and choose **Put away**. The folders it shares are put away
   with it.

Putting the machine away unenrolls it in masks, which revokes every token it holds, and closes xixo
link's connection. xixo link then stops and stays stopped. When masks cannot be reached, the machine
stays attached and the error says so. Try again once masks answers.

To delete what you put away, choose **Put away** at the top of **Resources**, then **Delete** on
each folder, then on the machine.

xixo link stays on the machine, stopped. To remove it, see
[uninstalling](https://github.com/xixo/xixo/tree/main/link#uninstalling) in the xixo link README.
