---
title: Self-hosting
description: Run xixo in production with Postgres, OpenSearch, storage, and sign-in through masks.
---

xixo ships as a container image. Point it at Postgres and OpenSearch, and it migrates itself on
boot. Sign-in is built in: xixo serves its own [masks](https://github.com/masksrb/masks) at `/id`.

## What it runs

| | |
| --- | --- |
| Web | The image's default command, `./bin/thrust ./bin/rails server`, on port 80 |
| Worker | `./bin/jobs`, from the same image |
| xixo link beside the server | `ghcr.io/xixo/xixo-link`, which reads and writes the server's files |
| Postgres | `xixo_production`, `xixo_production_cache`, `xixo_production_queue`, `xixo_production_cable`, and `xixo_production_masks` for the built-in masks |
| OpenSearch | The search index |

When the container runs the web command, `bin/docker-entrypoint` runs these before the server
starts:

- `bin/rails db:prepare` creates or migrates the databases.
- `bin/rails xixo:tenants` creates every declared [tenant](/concepts/tenants/), in xixo and in the
  built-in masks.
- `bin/rails xixo:resources` declares the resources in `config/resources.yml` in every tenant.

Any other command starts without them.

## Image tags

| Tag | Pushed on |
| --- | --- |
| `:<version>`, such as `:0.2.0`, and `:<major>.<minor>`, such as `:0.2` | each server release |
| `:main`, `:sha-<full commit sha>`, and `:latest` | every push to main |

`ghcr.io/xixo/xixo` is built for amd64. `ghcr.io/xixo/xixo-link` is built for amd64 and arm64.

A server release has a `server-v<version>` tag and its changes in `CHANGELOG.md`. An image built
from main holds the same xixo link builds and mac reader as a release, and names its commit after
the release it follows, such as `0.2.0+1a2b3c4`. A machine on `0.2.0` takes that build, and takes
`0.2.1` after it. Pin a version in production and read the changelog before you change it, or
follow `:main` to run every push. `:latest` follows main.

## The database role

In production xixo always connects as the role `xixo`, with the password in
`XIXO_DATABASE_PASSWORD`. `POSTGRES_USER` is not read there. The official Postgres image makes
`POSTGRES_USER` a superuser, so xixo cannot use it.

1. Connect to Postgres as an administrator and create the role:

   ```sql
   CREATE ROLE xixo WITH LOGIN PASSWORD 'change-me' CREATEDB;
   ```

   `CREATEDB` lets `db:prepare` create the databases on first boot. To create them yourself, create
   each one with `OWNER xixo` and leave `CREATEDB` off.

2. Check that the role holds neither `SUPERUSER` nor `BYPASSRLS`:

   ```sql
   SELECT rolsuper, rolbypassrls FROM pg_roles WHERE rolname = 'xixo';
   ```

   Both must be `f`. Row-level security keeps each tenant's rows apart, and a role with either
   attribute skips it. xixo and the built-in masks refuse to enter a tenant as such a role.

## Encryption and secrets

The database holds every resource's credentials and each tenant's masks client secret. xixo
encrypts those columns with Active Record Encryption. The built-in masks derives its own keys from
`SECRET_KEY_BASE`.

| Secret | Protects |
| --- | --- |
| `SECRET_KEY_BASE` | Session cookies, and every key the built-in masks uses. Anyone who holds it can forge a session. Changing it signs everyone out of masks and makes its encrypted columns unreadable. |
| `ENCRYPTION_PRIMARY_KEY`, `ENCRYPTION_DETERMINISTIC_KEY`, `ENCRYPTION_KEY_DERIVATION_SALT` | xixo's encrypted columns. |

1. Generate `SECRET_KEY_BASE` in a xixo checkout:

   ```sh
   bin/rails secret
   ```

2. Generate the encryption keys in the same checkout:

   ```sh
   bin/rails db:encryption:init
   ```

3. Set the three values it prints as variables:

   | Printed as | Variable |
   | --- | --- |
   | `primary_key` | `ENCRYPTION_PRIMARY_KEY` |
   | `deterministic_key` | `ENCRYPTION_DETERMINISTIC_KEY` |
   | `key_derivation_salt` | `ENCRYPTION_KEY_DERIVATION_SALT` |

Production refuses to boot when any of the four is unset or starts with `dev_only_`, the prefix of
the development values in `.env.example` and `compose.yml`.

:::caution
Keep the keys with your database backups, and never change them. Losing them makes every resource
credential and every tenant's masks client secret unreadable, for good.
:::

## Tenants and hosts

A tenant is a separate catalog with its own resources, feeds, and settings, at its own host. See
[tenants](/concepts/tenants/).

1. Declare the tenants with one of these. Setting both stops `xixo:tenants` with an error.

   | | |
   | --- | --- |
   | `XIXO_TENANT=xixo` | One tenant answers on every host. |
   | `XIXO_TENANTS=demo,acme` | Each tenant answers on hosts whose first label is its name, such as `demo.xixo.example.com`. |

2. Set `XIXO_HOST_SUFFIX` to the domain xixo answers under, such as `xixo.example.com`. Rails then
   answers `403` to any other `Host`, except at `/up`. Unset, Rails accepts every host.
3. Set `XIXO_PUBLIC_ORIGIN` to the origin browsers use. `%{subdomain}` stands for the first label of
   the host, such as `https://%{subdomain}.xixo.example.com`. With one tenant, leave out the
   placeholder, such as `https://xixo.example.com`. Production refuses to boot without it.
4. Point DNS for each tenant's host, or a wildcard under the suffix, at your reverse proxy.

The proxy must terminate TLS and pass the original `Host` header, because xixo finds the tenant from
the host. `RAILS_ASSUME_SSL` and `RAILS_FORCE_SSL` default to `true`.

To add a tenant later, add it to `XIXO_TENANTS` and recreate the web container.

## Example `compose.yml`

```yaml
x-xixo: &xixo
  image: ghcr.io/xixo/xixo:0.2
  restart: unless-stopped
  environment:
    POSTGRES_HOST: postgres
    XIXO_DATABASE_PASSWORD: ...
    OPENSEARCH_URL: http://opensearch:9200
    OPENSEARCH_USERNAME: admin
    OPENSEARCH_PASSWORD: ...
    SECRET_KEY_BASE: ...
    ENCRYPTION_PRIMARY_KEY: ...
    ENCRYPTION_DETERMINISTIC_KEY: ...
    ENCRYPTION_KEY_DERIVATION_SALT: ...
    XIXO_TENANTS: acme
    XIXO_HOST_SUFFIX: xixo.example.com
    XIXO_PUBLIC_ORIGIN: https://%{subdomain}.xixo.example.com
    MASKS_MAIL_FROM: xixo@example.com
    MASKS_SMTP_ADDRESS: smtp.example.com
    MASKS_SMTP_USERNAME: ...
    MASKS_SMTP_PASSWORD: ...
    XIXO_LOCAL_LINK: /handoff
  volumes:
    - storage:/rails/storage
    - link-handoff:/handoff

services:
  xixo:
    <<: *xixo
    healthcheck:
      test: ["CMD", "curl", "-fsS", "http://localhost/up"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 180s
    deploy:
      resources:
        limits:
          memory: 1g
    depends_on:
      postgres:
        condition: service_healthy
      opensearch:
        condition: service_healthy

  worker:
    <<: *xixo
    command: ["./bin/jobs"]
    healthcheck:
      test: ["CMD", "bin/jobs-healthy"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 120s
    deploy:
      resources:
        limits:
          memory: 2g
    depends_on:
      xixo:
        condition: service_healthy

  link:
    image: ghcr.io/xixo/xixo-link:0.2
    restart: unless-stopped
    environment:
      XIXO_LINK_XIXO: https://acme.xixo.example.com
      XIXO_LINK_ISSUER: https://acme.xixo.example.com/id
      XIXO_LINK_HANDOFF: /handoff/acme
      XIXO_LINK_WRITABLE: /data/files/acme
    volumes:
      - link-state:/var/lib/xixo-link
      - link-handoff:/handoff
      - files:/data/files
    deploy:
      resources:
        limits:
          memory: 6g
    depends_on:
      xixo:
        condition: service_healthy

  postgres:
    image: postgres:17-alpine
    restart: unless-stopped
    environment:
      POSTGRES_PASSWORD: ...
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 10s
      timeout: 5s
      retries: 10
    deploy:
      resources:
        limits:
          memory: 1g
    volumes:
      - postgres:/var/lib/postgresql/data
      - ./initdb:/docker-entrypoint-initdb.d:ro

  opensearch:
    image: opensearchproject/opensearch:2.19.1
    restart: unless-stopped
    environment:
      discovery.type: single-node
      OPENSEARCH_INITIAL_ADMIN_PASSWORD: ...
      plugins.security.ssl.http.enabled: "false"
      OPENSEARCH_JAVA_OPTS: -Xms512m -Xmx512m
    healthcheck:
      test: ["CMD-SHELL", "curl -fsS -u \"admin:$${OPENSEARCH_INITIAL_ADMIN_PASSWORD}\" http://localhost:9200/_cluster/health"]
      interval: 10s
      timeout: 5s
      retries: 30
    deploy:
      resources:
        limits:
          memory: 1536m
    volumes:
      - opensearch:/usr/share/opensearch/data

  caddy:
    image: caddy:2-alpine
    restart: unless-stopped
    ports:
      - "443:443"
      - "80:80"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy-data:/data
    depends_on:
      - xixo

volumes:
  storage:
  files:
  link-state:
  link-handoff:
  postgres:
  opensearch:
  caddy-data:
```

`initdb/01-xixo.sql` holds the `CREATE ROLE` statement from [the database role](#the-database-role),
with the password in `XIXO_DATABASE_PASSWORD`. Postgres runs it when its volume is first created.
The `Caddyfile` sends every tenant's host to xixo:

```
*.xixo.example.com {
  reverse_proxy xixo:80
}
```

Notes on the file:

- `OPENSEARCH_INITIAL_ADMIN_PASSWORD` sets the `admin` password when the volume is first created.
  OpenSearch refuses to start when it is weak.
- Traffic between the containers is plain HTTP. Keep Postgres and OpenSearch on a network that only
  xixo reaches, and publish no port for either.
- masks sends invitations, password resets, and sign-in codes from `MASKS_MAIL_FROM` through the
  `MASKS_SMTP_` server. Without them, masks sends no mail.
- The worker waits for the web container to report healthy, so it never runs before the migrations.
- OpenSearch gets three times its heap. xixo link gets 6 GB, because a program it runs on one file
  may use up to 4 GB, and exiftool up to 6 GB.
- Chromium in the worker keeps its sandbox. Leave `XIXO_CHROME_NO_SANDBOX` unset, and never run the
  worker privileged.

## Sign in for the first time

Each xixo tenant is a client of a masks tenant with the same name. By default xixo serves that masks
itself, at `/id` on each tenant's origin, such as `https://acme.xixo.example.com/id`.

1. Start the stack:

   ```sh
   docker compose up -d
   ```

2. Find the setup token that `xixo:tenants` prints for each masks tenant with no account yet:

   ```sh
   docker compose logs xixo | grep "masks:"
   ```

   To choose the token yourself, set `MASKS_SETUP_TOKEN` to at least 24 characters before you
   start.

3. Open the tenant in a browser and click **Get started…**.
4. Enter the setup token when masks asks for it.
5. Create the first account. That account owns the masks tenant.
6. Approve **xixo** when masks asks. You are signed in.

The account that owns the masks tenant becomes xixo's administrator on its first sign-in. Invite
everyone else from masks at `/id/manage`.

The built-in masks reads the other variables a masks server reads, such as `MASKS_SMTP_PORT`. See
the [masks ENV vars](https://masks.pages.dev/reference/environment/). It ignores `MASKS_TENANT`,
`MASKS_TENANTS`, and `MASKS_PUBLIC_ORIGIN_TEMPLATE`, because xixo sets them from its own variables.

### A masks server of your own

Run masks apart from xixo to sign several apps in through one masks.

1. Set `MASKS_ISSUER_TEMPLATE` to the issuer URL of the masks tenant each xixo tenant signs in
   through. `%{subdomain}` works as it does in `XIXO_PUBLIC_ORIGIN`:

   ```sh
   MASKS_ISSUER_TEMPLATE=https://%{subdomain}.auth.example.com
   ```

   With it set, xixo does not serve `/id` and creates no `xixo_production_masks` database.

2. Set `XIXO_LINK_ISSUER` on xixo link beside the server to the same issuer.
3. Start xixo and open each tenant in a browser.
4. Sign in with a masks account that may approve connections, and approve **xixo**.

For MCP clients to register themselves, the masks tenant must allow dynamic registration. See
[connecting an agent](/guides/connect-an-agent/#allow-dynamic-registration-in-masks).

## xixo link beside the server

xixo opens no file itself. The `link` container runs xixo link, which reads every file for the
server, writes uploads into the `files` volume, and runs the programs that read documents, images,
and recordings. See [machines](/concepts/resources/#what-xixo-may-do-with-a-machine).

Run one for each tenant, each with its own `XIXO_LINK_HANDOFF` and state volume:

| | |
| --- | --- |
| `XIXO_LINK_XIXO` | The tenant's origin. |
| `XIXO_LINK_ISSUER` | The tenant's masks issuer: the origin followed by `/id` with the built-in masks. |
| `XIXO_LINK_HANDOFF` | `/handoff/<tenant>`, in the volume the web and worker containers mount at `XIXO_LOCAL_LINK`. |
| `XIXO_LINK_WRITABLE` | Folders it may read and write, separated by colons. Each one is created on boot when it is missing. |
| `XIXO_LINK_FOLDERS` | Folders it may only read, separated by colons. Mount each one read-only. |

It enrolls itself after the first sign-in connects the tenant to masks:

1. xixo link leaves a request in `/handoff/<tenant>`.
2. The worker answers with a single-use enrollment token.
3. xixo link registers its own key with masks, and keeps it in its state volume.

Deleting the state volume makes it enroll again. It shows on the **Resources** page as
**This server**. Each folder it shares joins the catalog by itself. A folder the deployment declares,
such as `files`, is everyone's, and any other is held for the administrator who signs in first. xixo
may do everything with the folders it shares, and writes into the ones named in
`XIXO_LINK_WRITABLE`.

## Storage

xixo uses storage in two places.

- **Staging.** Uploads wait in Active Storage until a job places them. The default,
  `XIXO_STAGING_SERVICE=local`, writes to `/rails/storage`, so the web and worker containers must
  share it. To stage in S3-compatible storage, set `XIXO_STAGING_SERVICE=s3` and the other
  `XIXO_STAGING_` variables on the [ENV vars](/reference/environment/#storage) page.
- **Catalog storage.** `config/resources.yml` gives every tenant a `filesystem` resource named
  **Files** as its default storage, at `/data/files/<tenant>` on xixo link beside the server. That
  folder must be in `XIXO_LINK_WRITABLE`, on a volume mounted into the `link` container. Until xixo
  link connects, a placed upload waits. To keep files somewhere else, see
  [attaching a resource](/guides/attach-a-resource/).

## Private networks

xixo refuses to reach a private, loopback, or link-local address for a resource. List the origins of
services on your own network, separated by commas:

| Variable | Lets through |
| --- | --- |
| `XIXO_S3_ORIGINS` | An `s3` endpoint, such as a MinIO container at `http://minio:9000` |
| `XIXO_MCP_ORIGINS` | An MCP server attached as a resource |
| `XIXO_SEARCH_ORIGINS` | A self-hosted web search backend |
| `XIXO_INFERENCE_ORIGINS` | Every model server, public or private, such as `https://api.openai.com,http://ollama:11434` |

A model server whose origin is not in `XIXO_INFERENCE_ORIGINS` is unusable, unless xixo reaches it
through a machine or a tailnet. A service on a Tailscale or Headscale network is reached through a
`tailnet` resource. See [reach a tailnet](/guides/tailnet/) and [security](/concepts/security/).

## Transcription

Audio and video are transcribed by a resource that serves the `transcription` role. Without one,
each recording is analyzed without a transcript. Any server that answers OpenAI's
`/audio/transcriptions` works, such as whisper.cpp's `whisper-server`:

1. Download a model on the machine with the best GPU. `ggml-base.en.bin` transcribes English, and
   the models without `.en` transcribe other languages.

   ```sh
   curl -fL -o ggml-base.en.bin \
     https://huggingface.co/ggerganov/whisper.cpp/resolve/main/ggml-base.en.bin
   ```

2. Start the server:

   ```sh
   whisper-server -m ggml-base.en.bin --host 0.0.0.0 --port 11435 \
     --inference-path /v1/audio/transcriptions
   ```

3. Attach an `openai-compatible` resource with the base URL `http://<host>:11435/v1`. Give it any
   name as its **Transcription model**, because whisper.cpp answers with the model it started with.
4. Add the origin to `XIXO_INFERENCE_ORIGINS`, or reach the server through a machine or a
   [tailnet](/guides/tailnet/).

## The worker

`./bin/jobs` starts Solid Queue, which runs every job and the schedule in `config/recurring.yml`.
`BULK_CONCURRENCY`, `ANALYSIS_CONCURRENCY`, and `ANALYSIS_THREADS` size its pools. See
[jobs](/reference/environment/#jobs).

- Raise `ANALYSIS_CONCURRENCY` when analyses wait in the queue. Chromium holds a core while it
  renders a snapshot.
- On a small host, set `SOLID_QUEUE_IN_PUMA=true` on the web container and run no worker.
- Syncs and exports save their place as they go, so a restarted worker carries on from there.
- `XIXO_ITERATORS_DISABLED=true` stops every sync, analysis, export, and reindex in every tenant.

Follow job progress in the worker's log:

```sh
docker compose logs -f worker
```

### Mission Control at /jobs

Mission Control is mounted at `/jobs` on every tenant's host. Its HTTP basic authentication is on,
and xixo sets no user or password for it, so it answers `401` to every request. It would list every
tenant's jobs, because Solid Queue's tables sit outside row-level security. Leave it closed, or
block `/jobs` at the proxy.

## Health check

`GET /up` checks the database, the search index, the queue, and the workers. It is served outside
any tenant, skips the host check, and is not logged.

```sh
docker compose exec -T xixo curl -fsS http://localhost/up
```

```json
{"status":"ok","checks":{"database":"ok","search":"ok","queue":"ok","worker":"ok"}}
```

| Check | Fails when |
| --- | --- |
| `database` | The primary database does not answer. |
| `search` | OpenSearch does not answer within two seconds, or its cluster is red. |
| `queue` | A job has waited more than ten minutes for a worker. |
| `worker` | No worker has sent a heartbeat in `XIXO_WORKER_QUIET_SECONDS`, 300 by default. It always passes with `SOLID_QUEUE_IN_PUMA` set. |

`/up` answers `503` when `database` or `search` fails, and `200` otherwise. A late queue or a quiet
worker shows in the body without failing, so a slow worker does not restart the web container.

`bin/jobs-healthy` checks the worker. It exits `0` when a worker on the same host sent a heartbeat
within the same window, and `1` with the reason when none did.

## Upgrade

1. Read `CHANGELOG.md` for every release between the one you run and the one you move to.
2. Back up the catalog. Starting the old image again does not undo a migration. See
   [back up](/guides/back-up-and-restore/#back-up).
3. Change the image tags in `compose.yml` to the new version.
4. Pull the images and recreate the containers:

   ```sh
   docker compose pull
   docker compose up -d
   ```

The web container applies new migrations on start, and the worker starts after it reports healthy.
To go back, [restore](/guides/back-up-and-restore/#restore) the backup and start the old version.

## Keep xixo up to date

A timer on the host pulls the tag the compose file names and recreates the containers that changed.
With `:0.2` it follows patch releases. With `:main` it follows every push.

1. Copy [`deploy/xixo-update.service` and `deploy/xixo-update.timer`](https://github.com/xixo/xixo/tree/main/deploy)
   to `/etc/systemd/system/`.
2. Set `WorkingDirectory` in the service to the folder that holds your `compose.yml`.
3. Start the timer:

   ```sh
   sudo systemctl enable --now xixo-update.timer
   ```

It runs two minutes after boot and every ten minutes after that. `journalctl -u xixo-update` shows
each run. The timer runs on the host, so no container holds the Docker socket. Linked machines
update themselves on their next hello, as [add a machine](/guides/add-a-machine/#keep-xixo-link-up-to-date)
describes.

### Upgrading from 0.1

From 0.2, xixo link beside the server reads and writes the `files` resource. A migration moves every
`filesystem` resource to a folder on xixo link beside the server, at the path the server used, so
`files` becomes `/data/files/<tenant>`. Before you upgrade:

1. Mount the volume that held `/data/files` into the `link` container at `/data/files`, read-write.
2. Set `XIXO_LINK_WRITABLE` to `/data/files/<tenant>` on each tenant's xixo link.
3. Give xixo link, which runs as uid 1000, ownership of the files:

   ```sh
   docker compose run --rm --user root --entrypoint chown link -R 1000:1000 /data/files
   ```

4. Remove the `/data/files` mount from the web and worker containers.
5. Remove `XIXO_FILESYSTEM_ROOTS` from the web and worker containers after the migration ran. The
   migration reads it to find where each tenant's files were.

A `filesystem` resource with a root in another directory moves to that path. Mount the directory
into the `link` container at the same path, and name it in `XIXO_LINK_FOLDERS` or
`XIXO_LINK_WRITABLE`. Until you do, the resource is unusable.

## If it doesn't work

- **Every page answers `404 Unknown tenant`**: no tenant variable is set, or the host's first label
  names no declared tenant.
- **Requests answer `403`**: the request's host is outside `XIXO_HOST_SUFFIX`.
- **`Tenant::Exposed`, naming the role**: the database role holds `SUPERUSER` or `BYPASSRLS`. Remove
  them with `ALTER ROLE xixo NOSUPERUSER NOBYPASSRLS;`.
- **`Tenant::TenancyConflict`**: both `XIXO_TENANT` and `XIXO_TENANTS` are set. Remove one.
- **The container exits with `XIXO_PUBLIC_ORIGIN is not set`**: set it to the origin browsers use.
- **The container exits with `Switch::Invalid`**: a switch holds a value other than `true` or
  `false`. The error names it.
- **No setup token in the logs**: the masks tenant already has an account. Sign in with it, or set
  `MASKS_RECOVER` as the masks docs describe.
- **Uploads stage but never land**: the worker is not running, or it cannot read the web
  container's `/rails/storage`. Check `docker compose ps` and `docker compose logs worker`.
- **"shares /data/files/&lt;tenant&gt; read-only"** or **"no longer shares"**: xixo link beside the
  server does not list the folder in `XIXO_LINK_WRITABLE`, or its volume is not mounted into the
  `link` container.
- **An `s3` resource on your network fails its check**: add its origin to `XIXO_S3_ORIGINS`.
- **Many files failed while a model server was away**: once it answers again, start them over. Each
  file whose last analysis failed or ran out of time waits for the model server again, and xixo
  starts them 50 at a time. Pass `since:` to go back only so far. `1` is the tenant's id.

  ```sh
  docker compose exec xixo bin/rails runner 'Tenant.switch(Tenant.find(1)) { puts Analysis.retry_failed!(since: 2.days.ago) }'
  ```
