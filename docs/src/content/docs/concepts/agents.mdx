`/mcp` is a Model Context Protocol endpoint over streamable HTTP. It accepts the same masks access
token as the browser app, as described in [tenants](/concepts/tenants/). uris answers a request
without a token with `401` and a `WWW-Authenticate` challenge that names
`/.well-known/oauth-protected-resource`. That document lists the resource URL, the masks issuer as
its authorization server, and every `uris:` scope an MCP tool checks, with a description. The
`uris:settings:` scopes are left out, since no tool checks them, and an authorization server that
bounds what registered clients may request refuses a request that asks for them. An OAuth client
uses the document to find masks and request a token. See [connecting an agent](/guides/connect-an-agent/).

Calls are rate-limited per token, or per IP address when there is no token, to `URIS_MCP_LIMIT` a
minute (120 by default). An `Mcp-Session-Id` belongs to the subject that opened it, and uris refuses
it from anyone else.

## Four tools

| Tool | Scope to see it | Purpose |
| --- | --- | --- |
| `search` | `uris:catalog:read` | searches the whole catalog, or lists the newest feeds of a type |
| `feed` | `uris:catalog:read` | reads one [feed](/concepts/feeds/) in full. With `do`, it adds a note, renames, analyzes, creates, places, or sets how long a feed lasts. |
| `connect` | `uris:catalog:write` | connects two feeds, or disconnects them |
| `resource` | `uris:resources:read` | lists the [resources](/concepts/resources/), and sends a command to one |

The [MCP reference](/reference/mcp/) lists each tool's inputs.

A token sees only the tools its scopes permit. `Tool::Resources.for` builds the `resource` tool for
each token. `list`, `describe`, `runs`, `get`, `parameters`, and `search` are always in its schema.
`check`, `sync`, `keep`, `export`, `cancel`, `put`, and `snapshot` appear only when the token has
`uris:resources:command`. A token with `uris:web:keep` also gets `snapshot`, and can send it only to
a resource that renders pages, which is the `web` type. A command the token cannot use is left out of
`tools/list`.

uris still checks each call:

- the `feed` tool's writing verbs (`note`, `rename`, `analyze`, `create`, `place`, and `last`) need
  `uris:catalog:write`;
- `search` on a resource that serves `search` needs `uris:web:read`;
- `get` on a resource that serves `fetch`, such as `curl`, needs `uris:web:read`.

A token with `uris:mcp:call` also sees the tools of every MCP server attached as a resource, passed
through unchanged.

## The agent

`Agent` runs a prompt against an inference resource that serves the `agent` role, and offers it the
same four tools. It runs for a fixed number of turns: six by default, or the number a feed's
schedule sets, up to 32. Each turn asks the model for a reply.

- A reply with no tool calls is the answer.
- uris checks each tool call against the tool's input schema before running it. An unknown tool,
  arguments that are not valid JSON, and arguments the schema refuses go back to the model as an
  error it can correct. They do not end the loop.
- A tool result longer than 8,000 characters is truncated, with a note that says how much was cut.
- Three failed calls in a row end the run as `flailed`. A successful call resets the count.
- The last turn offers no tools and tells the model to answer from what it has already read.
- A run whose analysis is cancelled or past its deadline stops at the start of its next turn, as
  `halted`.
- A run with an analysis is told how much time it has, and is offered `more_time`. The loop answers
  `more_time` itself. Given a number of minutes and a reason, it moves the deadline later, up to one
  day from the start. When less than a minute is left, the next turn is the last, so the model
  answers from what it has before the deadline passes.

The run returns an `Answer` with the reply, the reason the run stopped, the turns taken, and every
call made.

When a feed is analyzed, the agent is asked to file it. It connects the feed to tags and related
feeds, and chooses a resource for a file that is still staged. An address feed with a schedule runs
the schedule's prompt instead. See [analysis](/concepts/analysis/).

This agent does not act for a person, so it does not use a person's token. `Feed#grant` gives it a
grant of its own, with the subject `feed:` followed by the feed's key and the scopes in
`Feed::AGENT_SCOPES`:

```
uris:catalog:read  uris:catalog:write  uris:web:read  uris:resources:read
```

The agent can search, read, file, and place feeds, and send read-only commands to resources. It
cannot sync, export, write into a resource, call an attached MCP server, or change settings.

### Whose resources a run reaches

Every analysis records `requested_by`, the subject of the person whose request started it. That is
`runFeed`, `analyzeFeed`, `askCatalog`, an upload, or the `feed` tool called with a person's token.
`Analysis#grant` builds the agent's grant from it, and the agent reaches the resources everyone here
can use and that person's own [personal resources](/concepts/resources/#only-mine-or-everyones).

An analysis started by a sync, a schedule, an edge, or another agent records nobody, and its agent
reaches only the resources everyone can use. Starting a run on somebody else's feed reaches your own
resources and never theirs.

The grant's subject stays `feed:` and the key either way, so the audit trail and the run budget
still name the feed. What the agent writes is cataloged for the whole tenant, including anything it
read from a personal resource.

## Asking

uris saves a question asked of the catalog as a note, and answers it with an analysis whose cause is
`ask`. The note's key is the question, and the note starts with no title. Before the lead sends its
first scout, the model that serves the `fast` role names the note in a few words, such as "Toronto
weather". If the note still has no title after the answer, because the tenant has no fast model or
the fast model failed, uris tries again with the first of the `fast`, `smart`, and `agent` roles that
a resource serves. See [asking a question](/guides/ask/).

`Asking` builds the prompts. Everything runs under the question's own grant, with the scopes in
`Feed::ASKING_SCOPES`:

```
uris:catalog:read  uris:catalog:write  uris:web:read  uris:web:keep  uris:resources:read
```

A lead and its scouts answer the question. The lead holds the question and the goal, and its only
tool is `scout`. It sends a scout a task, such as finding out what an address is and keeping its
about page, and gets back a short report. The lead never sees a raw search result or page, so its
transcript stays small no matter how much the scouts read. The lead may take 16 turns, within its
feed's timeout. If it answers before sending any scout, uris sends it back once to send one.

`Scouting` runs each task as a separate agent with a new context, using the real tools under the
same grant, for up to eight turns. Scouts sent in the same turn run in parallel,
`URIS_SCOUTS_AT_ONCE` at a time (two by default). Each runs in its own thread, which enters the
tenant on its own database connection. A scout uses the inference resource that declares the `scout`
role, or the agent's model when none does. A scout is told how much time it has and cannot ask for
more. It stops 90 seconds before the deadline, so the lead still has time to answer. Its report is
truncated to 1,500 characters. uris keeps the calls it made for the judges and the connections.

Scouts are told only about the resources the tenant has attached. With a search resource, a scout
can search the web. With a fetch resource, such as `curl`, it can read a page. With a `web`
resource, it can keep a page as a snapshot. The snapshot becomes a feed of its own, and keeping the
same address again later updates that feed. Without any of these resources, the question is answered
from the catalog alone.

A note that was asked holds a conversation. `askCatalog` with the note's `feedId` asks a follow-up
question in it, once the previous question has been answered. uris saves each question on the
analysis that answers it, and **Ask again** asks the latest question again. The lead of a follow-up
is given the earlier questions and their answers, up to eight of them, with each answer truncated to
1,500 characters. It is told to read the new question in their context without answering them
again, and its scouts are told which questions it follows. A follow-up about an earlier answer, such
as a request to write it in markdown, make it shorter, or turn it into a table, is answered by
rewriting that answer without any scout, and the lead is not asked to send one. The judges of a
follow-up see the conversation before it. When the reply is saved, `Analyzer::Conversation` rolls the
whole conversation into the analysis. Every question and answer becomes its text, and the summary,
entities, and tags are made from all of it. Search then finds the note by the whole
conversation.

Each answer records the feeds it cited, opened, or kept in a `drew_on` step, and the note's page
lists them under that answer. The note is also connected to all of them.

The run is confined. `Current.confined_to` holds the feeds the run created, and the `feed` tool's
writing verbs refuse any other feed. A page that tells the agent to rewrite a note or rename a file
therefore has no effect. The run can create only notes, never a scheduled feed. `connect` needs one
end to be the question or a feed the run created. Snapshots are not confined, because the page
decides what a snapshot contains.

Small models tend to stop early. uris sends a scout's report back, once for each of these problems:

- nothing came from the catalog and the scout never tried the web;
- the scout searched the web and read no page. The message includes the exact calls for the
  addresses the search returned;
- the scout read pages and kept none, while a resource could keep them.

When the lead finishes, uris connects the question to every feed the answer cites, every feed a
scout opened or created, and every page a scout kept. Then ten judges run on the `smart` model, or
on the agent's model when no smart model is declared. Each judge sees the question, the lead's
answer, and only what the scouts' tools returned. Each votes on whether that evidence supports the
answer, and whether what the run kept is worth keeping. uris stores the vote shares on the analysis
as the `verified` step, and exposes them as `Analysis.verified` and `Analysis.useful`. A judge that
fails does not vote. `ASK_VERIFICATIONS` sets the number of judges.

## Budgets and gates

Work that can run for a long time spends from a budget. This covers `feed` with `do: analyze`, and
`resource` with `sync` or `export`. Each subject in a tenant may start `URIS_RUN_BUDGET` of these per
clock hour, 20 by default, and `0` removes the limit. A feed's agent spends from its own subject's
budget, which is separate from any person's.

A gate is a row that stops a kind of job. The iterating jobs each name their gate: `sync`,
`analyze`, `export`, or `reindex`. A gate applies to the whole key or to one record, such as a
single resource for `sync`, and the record's gate takes precedence over the key's. A disabled gate
marks the run as gated and does nothing. A gate that is enabled but not live lets `sync` and
`reindex` walk and count without writing anything. Jobs read their gates again every 50 iterations,
so closing a gate stops a run that is already in progress. `URIS_ITERATORS_DISABLED` closes every
gate at once. Gates have no screen yet. Set them with `Gate.set!` from a console.

## Audit

Every tool call writes an audit event with the tool, the scope, the result (`ok`, `error`, or
`denied`), the IP address and request id, and the duration. Each event names its actor: a `person`
with their name and the client they asked through, a `client` acting for itself, the `agent`, or
`nobody` when no token was accepted. An agent's event also names the analysis it ran for, so the
**Activity** page in Settings shows one analysis as one entry. Each event carries a sentence about
the call, such as "filed invoice.pdf under receipts", and the feed it was about. uris writes the
sentence when the call is made, so it still reads correctly after the feed is forgotten. uris summarizes
the arguments and does not store them in full. It truncates strings to 200 characters, counts
arrays, and keeps one level of nesting. It replaces the value of any key that names a secret,
password, token, credential, authorization, or access key with `[redacted]`. Refused
authorizations, rate-limited calls, and some GraphQL mutations are recorded the same way.

The `auditEvents` query returns events to a token with `uris:catalog:read`. A daily job deletes
events older than `URIS_AUDIT_RETENTION_DAYS`, 90 by default, and `0` keeps them forever.
