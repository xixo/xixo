title: Resources
description: The places xixo reads from, writes to, and sends requests to.

A resource is one instance of a type, such as a bucket, a folder, a mailbox, a model backend, or an
MCP server. Its key is unique within its tenant and type. The [resource
reference](/reference/resources/) lists every type, what it serves, what it accepts, and what it
needs. This page covers what all types share.

## What a type serves

A type serves capabilities, such as `storage`, `inference`, `browser` for rendering pages, `fetch`
for reading a page's text, `search`, `tools` for an MCP server, or `transport`. A storage type also
says which mime types it accepts and the largest file it takes. Types such as git, IMAP, RSS, and
CalDAV serve no capability. xixo reads them by syncing.

A tenant has at most one default storage and one default inference resource. Only an administrator
chooses them. Snapshots go to the default storage unless the `web` resource names another, and so
does an upload that nothing else placed. Inference uses the default when more than one resource
serves a role. When the default is down, because its last check failed, its machine is offline, or
it needs connecting again, inference uses the first other resource for that role that is up. It
returns to the default once a check passes. Embeddings never move this way, because a different
embedding model makes every vector useless.

A model backend's **Model** serves every role the backend names no model for, except `embedding` and
`transcription`. It serves `vision` only when its server says the model reads images, which Ollama
and LM Studio do. When **Vision model** is empty, a check picks one the server says reads images. A
**Vision model** the server says cannot read images fails the check. The backend's card says which
model describes images, or why none does.

## Where they come from

`config/resources.yml` declares resources for every tenant, with hosts and secrets read from the
environment. The shipped file declares a `files` folder as the default storage. Each boot creates or
updates every declared resource and never deletes one, so a resource removed from the file stays
attached. A declared default takes effect only while the tenant has none, so a default chosen in the
app survives every boot. The development stack attaches a few more, as described in the
[quickstart](/quickstart/#resources).

People attach everything else in the browser, from a form that each type describes. Each value goes
into the resource's details, or into its encrypted credentials when the field is a secret. Attaching
runs a first check and reports the result. The same form changes a resource later. A secret left
empty keeps its value, and the form reads back only the names of the secrets that are set. See
[attach a resource](/guides/attach-a-resource/).

A `filesystem` resource is a folder on a machine that runs xixo link, the server's own included. It
names one of the folders xixo link shares, and xixo link lists, reads, hashes, and writes its files.
A folder is storage only when the machine's configuration marks it writable. The shipped `files`
resource is `/data/files/<tenant>` on xixo link beside the server.

Each folder a machine shares joins the catalog by itself. On each hello, xixo makes sure every
shared folder has a `filesystem` resource reached through that machine, keyed by the machine and the
folder's name, such as `media-documents`. A folder already attached is used, never doubled. A new
folder syncs at once and then every hour. When the machine stops sharing a folder, xixo puts its
resource away and keeps its items, and it brings the resource back when the folder is shared again.
A folder somebody put away stays put away. Putting the machine away puts its folders away with it.

A walk skips version control folders such as `.git`, dependency folders such as `node_modules`, and
files an operating system leaves behind, such as `.DS_Store`. **Also skip** adds names or patterns
of its own. xixo link also watches its shared folders. For a folder resource with a sync interval,
it tells xixo which paths changed a couple of seconds after they settle, so a new or removed file
shows up without waiting for the next sync. The scheduled sync still runs to catch anything a watch
missed. See [the xixo link README](https://github.com/xixo/xixo/tree/main/link#readme).

## Resources connected through masks

Google Drive, OneDrive, and an MCP server whose authentication is `masks` use a person's own
account. Nobody enters a secret into xixo.

1. **Attach** it. It starts out not connected.
2. **Connect** it. The browser goes to masks, which asks for the person's consent, signs them in to
   the provider if needed, and comes back.
3. From then on it syncs and answers requests with nobody signed in.
4. If the person revokes xixo's access in masks, the resource shows **Reconnect** and stops syncing
   until somebody reconnects it.

masks keeps the provider's tokens. xixo keeps a
[delegation](https://masks.pages.dev/guides/connecting-via-sdk/#delegation), a secret encrypted in
the resource's credentials that xixo trades for a new provider token when the last one expires.
masks revokes a delegation secret that is used twice, so only one worker renews a resource's token
at a time.

- Connecting needs `xixo:resources:command`, and the caller must
  [manage the resource](#who-changes-a-resource).
- The callback refuses a request this browser did not start, one that somebody already finished,
  and a connection masks made for a different person.
- When masks refuses, the resource needs connecting again and its syncs stop without retrying. When
  masks does not answer, the sync is retried as usual.

## Only mine, or everyone's

The person who attaches a resource chooses who can use it. **Everyone here** is the default for an
administrator. **Only me** is the default for anyone else, who cannot attach a shared one. A type
connected through masks starts as **Only me**.

A folder a machine shares starts out held for the machine's operators, the masks subjects under
**Who operates it**. The approving administrator is the first. Only they see the folder and what it
syncs, and its feeds' readers are those operators. When the list changes, xixo changes the readers
to match. An administrator who operates the machine can show the folder to everyone, or keep it for
the operators again, with `setFolderForEveryone`. An administrator who is not an operator does not
see the folder or its items.

A personal resource is hidden from everybody but its owner: from the resources query, every mutation
and tool that names a resource, and the tools a personal MCP server offers.

What a personal resource syncs is its owner's to read. Each feed records its readers. A feed is
everyone's when a shared resource holds it, or when nothing holds it. Otherwise its readers are the
owners of the personal resources that hold it. An extracted child has the readers of the file it
came from.

xixo checks readers everywhere a feed is read: every query, mutation, and tool that names a feed,
search and the passage index, `/references/:id/content`, the evidence an answer reads, the counts a
model is told, exports, and subscriptions. A feed lists only the references in resources its reader
can reach. A personal resource is never the default for uploads or questions. An agent reaches a
personal resource only in a run its owner started. See
[whose resources a run reaches](/concepts/agents/#whose-resources-a-run-reaches).

## Who changes a resource

A resource everyone shares belongs to the tenant, so only an administrator changes it. A token with
`xixo:settings:admin` attaches a shared resource, changes it, puts it away, deletes it, connects it,
sets its schedule, and changes a `web` resource's watchlist. It also chooses the default storage and
the default inference. A token with `xixo:resources:command` and no admin scope does all of these to
its own personal resources, and checks or syncs any resource it can see. The `manageable` field on a
resource says whether the asking token may change it.

Signing in never asks for `xixo:settings:admin`. masks grants it only to a person whose scopes in
masks cover it, which the person who connected xixo to masks has from the start. The `administrator`
query says whether the current token carries it. See [signing in](/concepts/tenants/#signing-in).

## Syncing

A type that can list what its source holds can sync. A `web` resource syncs only while its
**Watchlist** holds an address. A sync interval is at least one minute, and xixo checks every minute
for resources that are due. See [schedule syncs](/guides/attach-a-resource/#schedule-syncs).

- Only one sync runs for a resource at a time. A sync whose worker died is given up after six hours,
  and another can start.
- A sync walks the resource page by page, records a [reference](/concepts/references/) for each
  object, and [analyzes](/concepts/adding/#sync) what needs it. After a deploy it resumes where it
  was.
- An object whose version has not changed, and which has been analyzed since, is only marked seen,
  so a sync of a large resource that barely changed costs little more than its listing.
- A failed request to the source gets five attempts before the run fails.
- A run can be cancelled, and it stops when it passes its deadline.
- When a sync finishes, the next one is due one interval later, skipping any times that were missed.

A type that can ask its source for only what changed, such as git, IMAP, GitHub, OneDrive, Google
Drive, Notion, or Slack, keeps a checkpoint. The next sync walks only what changed since it, as long
as a full walk finished within the last day. Otherwise, or when the checkpoint cannot be used, such
as after history was rewritten, it walks everything. A checkpoint is saved only when a walk
finishes. A folder, a bucket, and a WebDAV share walk everything on every sync.

A Google document, spreadsheet, presentation, or drawing syncs as the Word, Excel, PDF, or PNG file
Drive exports it to, so the analyzers read it like any other file.

## Reaching through another resource

A resource can be reached through a transport, set as **Reached through** in the app or `via` in
GraphQL and `config/resources.yml`. Two types are transports:

- A `tailnet` reaches the addresses on a Tailscale network. See [reach a tailnet](/guides/tailnet/).
- A `machine` reaches its shared folders as `filesystem` resources, and a model server on it as an
  `openai-compatible` resource at `127.0.0.1`. xixo link passes on only a model server's own
  requests, such as chat and embeddings, to a port where it found a model server, and only while the
  machine offers its models. It carries no audio, so it cannot transcribe.

A resource reached through a transport connects only to addresses the transport covers. The address
check runs as usual, with the transport's ranges in place of the public internet, so a public
address is refused as firmly as a loopback one. `XIXO_ALLOW_PRIVATE_FETCH` and the `_ORIGINS` lists
do not widen it. A `git` resource behind a transport takes only an `http` or `https` URL. The
[resource reference](/reference/resources/) says which types can be reached through a transport.

Checking such a resource checks the transport first. When the transport fails, the resource fails
with `<key> is reached through <transport>, which is down`, followed by the transport's error. A
transport cannot be put away or deleted while another resource is reached through it.

### A machine that is offline

Before a check or a sync dials a resource reached through a tailnet, xixo asks Tailscale whether
the machine at that address is online. When it is offline, xixo dials nothing. The app shows the
resource as **offline**, with when the machine was last seen.

- A sync that finds the machine offline fails once without retrying, and no sync is scheduled while
  it stays offline.
- xixo checks again ten minutes after the last check. When the machine is back, a scheduled sync
  starts at once.
- Inference passes over a model server that is offline, the same way it passes over one that failed
  its check.

A resource reached directly is never offline, and neither is one whose host the tailnet does not
list. Each fails its check with the error the connection raised.

### What a transport reaches

The `discovered` query, and the `resource` tool's `discover` command, list the machines a transport
reaches. For a tailnet these are its peers, online ones first, each with its names, its addresses on
the tailnet, and when it was last seen. xixo reads nothing else from Tailscale, so a peer's keys,
owner, tags, and operating system stay on the server. Asking for `services` also tries well-known
ports on each online machine, such as Ollama's, LM Studio's, and IMAP's, and lists each one that
answers with the type and address to attach it with. Discovery changes nothing.

## Machines and xixo link

A `machine` resource stands for a machine running xixo link, the program in `link/`. The
**Resources** page shows a card for each machine, with xixo link beside the server first as **This
server**. Every other resource sits on the card of the machine it lives on or is reached through.

A machine links itself up, and an administrator approves it:

1. An administrator copies one command from **Resources** and runs it on the machine. The script it
   fetches holds no secret. It downloads the build for the machine, and on a Mac the mac reader, and
   checks each against its SHA-256.
2. xixo link makes its own keys, and asks to link up with the machine's description: its name,
   system, hardware, GPUs, disks, folders, the readers installed on it, and the model servers found
   on it. It prints a user code, such as `WDJB-MJHT`.
3. The request appears to every administrator on **Resources**, with the same code and the address
   it came from. The code is how the administrator matches the request with the machine in front of
   them.
4. On approval, xixo hands xixo link a one-time enrollment token from masks. xixo link registers
   itself with masks and gets a client whose private key never leaves the machine.
5. xixo creates the `machine`, named and keyed by the first label of the host name, and makes the
   approving administrator its first operator. It answers xixo link with the machine's name and
   the address of its card, which xixo link prints.

A request runs out after ten minutes, and each address and tenant can have only a few waiting at
once. Running the command again on a linked machine updates xixo link and its configuration, and keeps
the approval. A
machine cannot be attached by hand. See [add a machine](/guides/add-a-machine/) for the steps.

An administrator also links a machine from their own computer with `xixo-link add`, over their own
`ssh`. `xixo-link login` signs them in first: xixo starts masks' device grant with its own client
and hands the command line the person's tokens, so the command line holds no client of its own.
`add` copies the build xixo serves to the machine after checking its SHA-256, runs `xixo-link
describe` there, and posts the description to xixo. xixo makes the plan, approves the request as
that administrator, and answers at once with the plan, the enrollment token, and the device code.
The command then installs xixo link on the machine, enrolls it with the token, and starts it. xixo
never holds an ssh key, and a machine's own token cannot add a machine. See [link a machine over
SSH](/guides/add-a-machine/#link-a-machine-over-ssh).

xixo link connects to xixo over a WebSocket, with a DPoP-bound masks token that carries `xixo:link`.
xixo takes the connection only from the client of an active machine in the tenant, and closes it
when the token expires or the machine is put away. xixo never connects to the machine. On each
hello, xixo link reports its version, folders, its description, whether it lends its files, and any
warnings, which show on its card. Every minute it adds its uptime, load, memory, and disks. A
machine not heard from for three minutes is offline.

### What xixo does with a machine

xixo plans what a machine does from the machine's description, with fixed rules. The plan has
three lines, each with a reason, and the approval page and the machine's card show them as
switches:

| Line | When it is possible | What it does |
| --- | --- | --- |
| Catalog | The machine shares folders. | Each shared folder joins the catalog by itself, read only or read and write as the machine says. |
| Extract | The machine has readers installed. | The machine reads its own files, and joins the pool that reads uploads, mail attachments, cloud files, web pages, and the files machines lend, as described in [extraction](/concepts/analysis/#extraction). |
| Models | A model server answers on the machine. | xixo attaches the model server through the machine, and makes it the default for inference when there is no other. |

A line that is not possible stays off, and its reason says why, such as "Its NVIDIA GeForce GTX
1070 has no driver, so models run on another machine." Every possible line starts on. An
administrator turns a line off at approval or on the card, and the change takes effect at once,
without touching the machine. xixo plans again on every hello, so a reader installed later or a
model server started later shows up by itself.

The machine decides the rest. The link-up command names the folders it shares, and a folder followed
by `:rw` is writable. xixo writes only into a writable folder. The shared folders, and which of them
are writable, are set only on the machine, and nothing xixo sends changes them. The machine's own
configuration can also keep its files' bytes on the machine with `lend`, and the card says when
it does.

### Tools a machine offers

A machine offers MCP clients these tools. A client reaches them as commands on the machine through
the `resource` tool at `/mcp`, never through a port on the machine. `write` needs a folder the
machine shares writable, and `chat` needs the plan's **Models** line on.

| Tool | Command | Does |
| --- | --- | --- |
| `browse` | `browse` | Lists the shared folders, or the files in one. |
| `search` | `search` | Finds files by xixo's index of the machine's folders, then by their paths on the machine. |
| `read` | `read` | Sends up to 256 KiB of a file. |
| `write` | `write` | Writes a file of at most 1 MiB into a writable folder. It overwrites a file only when asked to. |
| `extract` | `extract` | Runs the machine's extractors on a file and answers with what they read. |
| `models` | `chat` | Asks a model server on the machine one question. |

- Every command needs `xixo:resources:read`, and `write` also needs `xixo:resources:command`.
- `browse`, `write`, `extract`, `chat`, and the walk of the machine's folders answer only the
  machine's operators and administrators. The operators are the masks subjects listed under **Who
  operates it**. Anyone else gets `search` over xixo's index, and `read` of what analysis drew out
  of the file.
- `read` sends the file's bytes unless the machine's configuration sets `lend` to false. From such a
  machine, or one that is offline, it answers with what analysis drew out of the file.
- `chat` sends the question only to a model server on the machine's own loopback address. It takes
  no address and follows no redirect.
- One call that waits on a machine runs on it at a time, and one for each person across every
  machine. Another is told the machine is busy.
- A folder attached as one person's `filesystem`, and a folder that holds a file kept to one person,
  are out of reach of every other person's token. A folder held for the machine's operators is out
  of reach of every token that is not an operator's, an administrator's included.
- `browse`, `search`, `read`, and `extract` count as reading the catalog, and `write` and `chat` as
  reaching outward, for an agent's [catalog or web](/concepts/agents/#catalog-or-web) rule.

No tool takes a command line, a program, or an address. xixo records each call in the audit log. See
[what xixo does with a machine](/guides/add-a-machine/#what-xixo-does-with-a-machine).

### xixo link beside the server

Every install runs xixo link beside the server, as the `xixo-link` service of the example compose.
It has no database, and sees only its own state and the folders mounted into it. It enrolls itself
through a folder it shares with the worker, so it needs no link-up command. Deleting its state
volume enrolls it again. See [xixo link beside the
server](/guides/self-hosting/#xixo-link-beside-the-server).

## Health, internal stores, archiving, and deleting

A check tests that a resource answers, and records when it ran and any error. A resource is healthy
when it has been checked and the last check passed. A model backend's check also tries tool calls,
the context window, embeddings, and transcription in the background, and reads as checking until
that finishes. Every ten minutes, xixo checks each resource that was never checked, was last checked
more than six hours ago, or failed a check more than ten minutes ago, except one that is syncing.
Checking an MCP server asks it again for its tools.

xixo keeps two stores for itself: `children`, for files extracted from other files, and `derived`,
for previews, thumbnails, and frames. Neither is offered for an upload, listed, archived, synced, or
made a default.

**Put away** archives a resource and deletes nothing. An archived resource is left out of placement,
the defaults, and the sync schedule, and can be brought back. Only an archived resource can be
deleted, so deleting always takes two steps. Deleting is refused while a run is open.

Deleting removes the resource's references, its runs, and its row, so its key is free again. Each
file left with no originals is then forgotten, unless a note, an expiry, or an edge someone made
keeps it. See [noticing what is gone](/concepts/references/#noticing-what-is-gone). The deletion and
each feed it forgets are recorded in the audit log.

Deleting does not reach into the source, so the files in a bucket, a folder, or a mailbox stay where
they are. A `database` resource is the exception, because its files live in xixo's own database. A
resource connected through masks keeps its connection in masks until it is removed there.
