title: Resources
description: The places xixo reads from, writes to, and sends requests to.

A resource is one instance of a type, such as a bucket, a directory, a mailbox, an inference
endpoint, or an MCP server. Its key is unique within its tenant and type. The
[resource reference](/reference/resources/) lists what each type needs and what it can do. This page
covers what all types share.

## What a type declares

A type declares what it serves with three class macros:

| | |
| --- | --- |
| `serves` | its capabilities: `storage`, `inference`, `browser`, `fetch`, `search`, `tools`, or `integration` |
| `accepts` | the mime patterns it will store, such as `*/*` |
| `up_to` | the largest file it will take, in bytes, or no limit when it is unset |

`browser` is the `web` type, which renders pages. `fetch` is the `curl` type, which reads a page's
text. `search` is a web search API. Types such as git, IMAP, RSS, and CalDAV declare no capability,
and xixo reads them by syncing.

Every save copies the declaration into the `serving` jsonb column. A question such as "which active
stores accept a 4 GB video" is then one SQL query, and xixo does not need to load every resource to
answer it. The copy is only as current as the last save. `bin/rails xixo:resources`, which the
production entrypoint runs before the server starts, saves every row again in every tenant and then
reconciles the declared resources.

A tenant has at most one default storage and one default inference resource, and only a resource
that serves the matching capability can hold either one. Making a resource the default clears the
flag on the previous one. Snapshots go to the default storage unless the `web` resource names
another, an upload that nothing placed goes there, and inference uses the default when more than one
resource serves a role. When the default's last check failed, its machine is offline, or it needs connecting again,
inference uses the first other resource serving the role that is not down, and returns to the
default once a check passes. Embeddings never move this way, because a different embedding model
forgets every vector.

## Where they come from

`config/resources.yml` is ERB, keyed by environment, and reads every host and secret from the
environment. The shipped file declares a `files` filesystem resource as the default storage.
`Resource.declare!` reconciles it in each tenant. It creates or updates each declared key and never
deletes. A resource removed from the file stays attached, so nobody using it loses it. A declared
`default_storage` or `default_inference` takes the default only while the tenant has none, so a
default chosen in the app survives every boot.

In development, `db/seeds.rb` attaches a database store, an S3 bucket in MinIO, a `web` resource,
and an Ollama inference resource. See the [quickstart](/quickstart/#resources).

People attach everything else in the browser. A type that can be attached returns an `attaching`
description, with a label and a list of fields, and the form is rendered from it.
`Resource::Settings` reads the submitted values against those fields, for both the file and the
form. It drops any value the type does not declare and refuses a missing required field. Each value
goes into `details`, or into `credentials` when the field is a secret. Credentials are encrypted at
rest, and the audit log records which fields were set but never their values. Attaching runs a first
check and reports the result. See [attaching a resource](/guides/attach-a-resource/).

A resource is changed through the same form. Its type and key stay the same. Its name and fields
are read against the type again. A secret left empty keeps its current value, and a field the type
no longer asks for is removed along with its value. The form reads back only the values held in
plain text, plus the names of the encrypted fields that have a value. xixo checks and audits a
change the same way it checks and audits attaching.

A filesystem resource is a folder on a machine that runs the xixo agent, the server's own included.
It is reached through that machine's `xixo-agent` resource and names one of the folders the agent
shares. xixo never opens a file itself: the agent lists, reads, hashes, and writes. A folder is
storage only when the machine's own config marks it writable. A read-only folder accepts no
uploads, so placement passes it over and it cannot be default storage. The shipped `files` resource
is `/data/files/<tenant>` on the agent beside the server, which the example compose mounts
read-write.

A walk never enters version control folders such as `.git`, dependency folders such as
`node_modules`, or the folders and files an operating system leaves behind, such as `.DS_Store`.
**Also skip** adds names or patterns of its own. A prefix walks only the folders that can hold it, and
a sync resumed from its cursor passes over the folders it already walked without opening them.

## Resources connected through masks

Google Drive, OneDrive, and an MCP server whose authentication is `masks` use a person's own
account. Nobody enters a secret into xixo.

1. **Attach** it. It starts out not connected.
2. **Connect** it. The browser goes to masks, which asks for the person's consent, signs them in to
   the provider if needed, and returns.
3. From then on it syncs and answers requests, with nobody signed in.
4. If the person revokes xixo's access in masks, the resource shows **Reconnect** and its syncs
   stop until somebody reconnects it.

masks keeps the provider's tokens. xixo keeps a
[delegation](https://masks.pages.dev/guides/connecting-via-sdk/#delegation), which is the connection and a secret
encrypted in the resource's credentials. When the last provider token expires, xixo exchanges the
secret for a new one.

xixo enforces these rules:

- `/resources/<id>/connect` needs `xixo:resources:command`, and the caller has to manage the
  resource: their own personal one, or a shared one with `xixo:settings:admin`.
- `/connect/callback` refuses a `state` that this browser did not start, a callback that somebody
  else already finished, and a connection that masks made for a different person.
- Only one worker at a time renews a resource's token, under a row lock, because masks revokes a
  secret that is used twice. xixo keeps every rotated secret.
- When a provider API refuses the token, xixo gets one new token and tries once more.
- When masks refuses, xixo sets `needs_connect_at` and raises `Resource::Unusable`, which stops a
  sync without retrying it. When masks does not answer, xixo raises `Resource::Failed`, which is
  retried as usual. A successful check or sync clears `needs_connect_at`.

## Only mine, or everyone's

The person who attaches a resource chooses who can use it. **Everyone here** is the default for an
administrator, and **Only me** for anyone else, who cannot attach a shared one.
**Only me** records the person's subject as `owner_subject`. From then on the resource is hidden from
everybody else: from the resources query, from every mutation that names a resource, from the
`resource` and `feed` tools, from the connect route, and from the MCP tools a personal MCP server
offers. A type connected through masks starts as **Only me**.

What a personal resource syncs is its owner's to read. Each feed records its readers in `readers`:
nothing, which means everyone, when a shared resource holds the file or nothing holds it at all, or
the owners of the personal resources that are the only places holding it. A feed extracted from
another, such as an attachment or a page, has the readers of the feed it came from. A copy of the
same file in a shared resource makes it everyone's.

xixo checks `readers` everywhere a feed is read. `Feed.readable_by` narrows the `feed`, `feeds`,
`search`, `types`, `analysis`, `analyses`, and `auditEvents` queries, a feed's connections and
children, every mutation that names a feed, the `search`, `feed`, and `connect` tools,
`/references/:id/content`, the evidence an answer reads, the counts the model is told, and an export,
which records who asked for it. The search index and the passage index carry the same readers on each
document, and every query filters by them, so another person's personal file is never a candidate.
`feedAnalyzed` sends nothing about a feed the subscriber cannot read. A feed lists only the references
held in resources its reader can reach, so nobody else reads its path or fetches its bytes with the
owner's credentials. A personal resource is never the default for uploads or questions. An agent working on a feed reaches it only
in a run its owner started. See [whose resources a run reaches](/concepts/agents/#whose-resources-a-run-reaches).

## Who changes a resource

A resource everyone shares belongs to the tenant, so only an administrator changes it. A token with
`xixo:settings:admin` attaches a shared resource, changes it, puts it away, deletes it, connects it
through masks, sets its schedule, and changes a `web` resource's watchlist. Only an administrator
chooses the default storage and the default inference. A token with `xixo:resources:command` and no
admin scope does all of these to its own personal resources, and checks or syncs any resource it can
see. `Resource#managed_by?` decides, and the `manageable` field on a resource answers it for the
token asking.

Signing in never asks for `xixo:settings:admin`. **Sign in as an administrator** on the **Resources**
page signs in again asking for it as well. masks grants it only to a person whose own scopes in masks
cover it, which the person who connected xixo to masks has from the start, and anyone else signs in
with the usual scopes. The `administrator` query says whether the current token carries it.

## Syncing

A type that implements `each_page` can sync. A type that does not can neither sync nor have a
schedule. A `web` resource syncs only while its watchlist holds an address. `sync_interval` is at least one minute, and `ScheduleSyncsJob` checks every
minute for resources that are due.

Starting a sync claims the resource with a single conditional update, so two workers cannot both
start one, and opens a run of kind `sync`. The job walks the resource page by page with
job-iteration. It records a [reference](/concepts/references/) for each object, analyzes any
[feed](/concepts/feeds/) that needs it, and resumes at its cursor after a deploy. An object whose
version matches the one recorded, and which has been analyzed since, is only marked seen, with one
update and no write to the search index, so a sync of a large resource that barely changed costs
little more than its listing. A
`Resource::Failed` error gets five attempts before the run fails. When the sync finishes, xixo
clears the claim and schedules the next sync on the original interval, skipping any times that were
missed. A failed sync also clears the claim, but does not record the resource as synced. If the
worker running a sync dies, the claim stays for six hours. After that xixo treats the sync as
abandoned, and another sync can start.

A run can be cancelled, and it stops when it passes its deadline.

`Resource::Walk` decides which kind of walk a sync does. A type that can ask its source for only
what changed, such as git, IMAP, GitHub, OneDrive, Google Drive, Notion, or Slack, keeps a checkpoint in `sync_state`. The
checkpoint is the commit it reached, the last message it saw together with the mailbox's
`UIDVALIDITY`, the time the last walk began minus five minutes, or the delta link Microsoft Graph
handed back. The next sync walks only what changed since the checkpoint, as long as a full walk
finished within the last day. Otherwise it walks everything. It also walks everything when the
checkpoint cannot be used, for example because history was rewritten, the mailbox was renumbered,
or Microsoft Graph expired the delta link. A walk saves its new checkpoint only when it finishes. A cancelled, failed,
or dry-run sync leaves the previous checkpoint in place, and a walk resumed after a deploy keeps the
checkpoint it started with. `walked_at` records when a full walk last finished without missing
anything.

Google Drive's walk of what changed reads Drive's change list from the page token its last full walk
began at, and a file removed or put in the trash is gone. A full walk lists every file the
resource's query reaches. A Google document, spreadsheet, presentation, or drawing is downloaded as
the Word, Excel, PDF, or PNG file Drive exports it to, so the analyzers read it like any other file.
Forms, folders, and shortcuts are left out.

Notion's walk of what changed asks for pages newest edit first and stops at the first one edited
before its checkpoint. Slack's asks for threads begun up to seven days before its checkpoint, so a
reply to a recent thread is read at the next sync and a reply to an older one at the next full walk.
A directory, a bucket, and a WebDAV share list everything on every sync, and an object whose version
has not changed costs one update.

## Reaching through another resource

A resource can name a transport in its `via` column. A transport is a resource that serves
`transport`. It lists the addresses it reaches in `covers`, and `reach!` can rewrite a URL before it
is dialed. The shipped transport is `tailnet`, which covers the Tailscale ranges `100.64.0.0/10` and
`fd7a:115c:a1e0::/48`. See [reach a tailnet](/guides/tailnet/).

A resource with a `via` connects only to addresses its transport covers. The address check runs as
it always does, with the transport's ranges in place of the public internet, so a public address is
refused as firmly as a loopback one. `XIXO_ALLOW_PRIVATE_FETCH` and the `_ORIGINS` lists do not widen
it. Where xixo resolves a name itself, it connects to the address it checked. An `s3` resource also
checks the address of the peer that answers, since the AWS SDK resolves names on its own.

These types can name a `via`: `webdav`, `caldav`, `carddav`, `s3`, `mcp`, `search`, `curl`, `rss`,
`imap`, `git`, `openai-compatible`, `xixo-agent`, and `filesystem`. Every other type refuses one. A
`xixo-agent` reaches only `filesystem` resources, and a `filesystem` is reached only through a
`xixo-agent`. A `git` resource behind a
transport takes only an `http` or `https` URL, since the address check does not apply to `ssh`.

Checking a resource with a `via` checks the transport first. If the transport fails, the resource
fails with `<key> is reached through <transport>, which is down`, followed by the transport's error.

### A machine that is offline

tailscaled's status says whether each machine on the tailnet is online, and when it was last seen.
Before a check or a sync dials a resource reached through a tailnet, xixo reads the host from the
field the type keeps its address in (`url`, `endpoint`, `base_url`, or `host`). It looks for a peer
with that address, host name, or name on the tailnet. When that peer is offline, xixo records its
name in `offline_host` and when it was last seen in `offline_last_seen_at`, and dials nothing.

A resource that is offline is down and not healthy, and its `check_error` stays empty. The app shows
it as **offline**, with when the machine was last seen. A sync that finds the machine offline raises
`Resource::Offline`, which fails the run once without retrying it. `ScheduleSyncsJob` skips a
resource that is offline. `ScheduleChecksJob` checks it again ten minutes after its last check, and
that check asks only tailscaled. When the machine is back, the check clears both columns, moves a
scheduled resource's next sync to now, and goes on to check the resource as usual. Inference passes
over a model server that is offline the same way it passes over one that failed its check.

A resource reached directly is never offline, and neither is one whose host the tailnet does not
list. Each fails its check with the error the connection raised.

### What a transport reaches

The `discovered` query takes a transport's key and lists the machines it reaches. For a tailnet,
these are the peers in tailscaled's status, the online ones first. Each has its host name, its name
on the tailnet, its addresses on the tailnet, whether it is online, and when it was last seen. xixo
reads nothing else from the status, so a peer's keys, owner, tags, and operating system stay on the
server. An address outside the tailnet's ranges is dropped. `address(type:)` gives what that type's
address field would hold to reach the machine, and `addressedBy` on `resourceTypes` names the field.

Asking for `services` also tries a TCP connection to a few well-known ports on each machine that is
online, for half a second each: 11434 for ollama, 1234 for LM Studio, and 993 for IMAP. Each port
that accepts is listed with the type that reaches it and the address to give that type. At most 32
machines are asked. The `resource` tool's `discover` command returns the same list, services
included. Discovery changes nothing, and it is refused for a transport the grant cannot reach.

`via` is set by the `via` argument of `attachResource` and `updateResource`, by the "Reached through"
field when a resource is attached or changed in the app, or by a `via` key in `config/resources.yml`.
The validations refuse a `via` that does not serve `transport`, that belongs to another tenant, that points at the resource itself, that forms a
loop, or that is more than four hops from a resource that answers. The foreign key is composite:
`(via_id, tenant_id)` references `(id, tenant_id)`, so the database refuses a link to another
tenant's resource even if the application does not. A transport cannot be archived while an active
resource uses it.

## Machines and their agent

A `xixo-agent` resource stands for a Linux machine running `xixo-agent`, the program in `agent/`.
Attaching one with an SSH key starts an `install` run. `InstallAgentJob` connects over SSH to the
address in `host`, which passes the address check through the machine's own `via`, and holds the
machine to the host key in `host_key`. Only a machine reached through a `tailnet` resource at a
tailnet address, in `100.64.0.0/10` or `fd7a:115c:a1e0::/48`, may leave `host_key` empty, and then
the key the machine offers is kept there. Any other install stops before it sends anything. The
client the agent enrolls as is kept on the resource as soon as `xixo-agent enroll` names it, so a
run that fails later still leaves it where archiving the machine unenrolls it. The run refuses a machine that is not Linux on x86_64 or aarch64 and an account without
`sudo -n`. It places the binary for the machine's architecture from `XIXO_AGENT_DIR`, checks its
SHA-256 on the machine, writes `/etc/xixo-agent/config.json`, and starts the `xixo-agent` systemd
service as the SSH user. The private key is removed from the resource's credentials when the run
ends, whether it worked or not. See [add a machine](/guides/add-a-machine/) for the steps.

### Enrollment

The run asks masks for an enrollment token at the issuer's `enrollment_endpoint`, as the tenant's
own client, for the `xixo:agent` scope alone. It passes the token to `xixo-agent enroll` on
standard input. The agent makes its keys on the machine and registers itself with masks, which
gives it a client that signs in with `private_key_jwt`, uses only `client_credentials`, and gets
DPoP-bound tokens. The private keys never leave the machine, and xixo keeps only the client's ID,
in `client_id`. `xixo:agent` is outside the scopes xixo asks for when a person signs in.

### The connection

The agent connects to `/cable` with `Authorization: DPoP <token>` and a DPoP proof for `GET` on
that URL. `ApplicationCable::Connection` takes such a connection only when the token's audience is
the tenant's resource, the token is bound to the key that made the proof, the proof is fresh and
used once, the token carries `xixo:agent`, its subject is its own client, and an active
`xixo-agent` in the tenant holds that client's ID. A connection without an `Authorization` header is
a person's browser, and the two never mix: `GraphqlChannel` refuses a machine, and `AgentChannel`
refuses a person. Every fifteen seconds the channel closes a connection whose token has expired or
whose machine was archived, and the agent connects again with a new token.

On `hello`, xixo records the machine's hostname, operating system, architecture, agent version,
folders, model servers, the tools it offers, whether it lends its files' bytes, and its warnings,
and clears `offline_host`. `health` adds uptime, load, memory, and disks every minute, and replaces
the warnings. A warning is a sentence the agent writes about something keeping it from working
fully, such as a shared folder it may not read; xixo keeps at most 16, each up to 500 characters,
and shows them on the machine's card. When the connection closes, the machine goes offline with when it was last
seen, unless a newer connection has taken its place. A machine not heard from for three minutes is
not connected either way. What xixo keeps is trimmed and checked first: folders must be clean
absolute paths, and services are only ollama and LM Studio.

### Asking the agent

Each question to an agent is an `agent_exchanges` row with a request ID. xixo broadcasts
`{request, verb, args}` on the machine's stream and waits for a `reply` with that ID, so a job in
the worker reaches an agent connected to a web process. `Resource::XixoAgent` asks in four ways:

| Method | Does |
| --- | --- |
| `ask(verb, args, within:)` | Sends any verb and returns the reply's result. Fails when the agent refuses or says nothing for thirty seconds. |
| `exchanged(verb, args, within:) { \|answer\| }` | Sends any verb and yields the answer, whose `file(entry)` gathers a file the agent streamed back. The exchange and every chunk are deleted when the block returns. |
| `read(folder, path)` | Asks for one file in a shared folder and returns it as a temporary file. |
| `upload(io)` | Holds bytes for the agent as chunks of at most 256 KiB and returns the upload's ID and size. The machine fetches it once from `/agent/uploads/:id` within fifteen minutes, with its DPoP-bound token and a proof for that URL, and each chunk is deleted as it is sent. |

Bytes from the agent arrive as `chunk {request, seq, data}` frames. A file the agent sends back
with an answer has an ID of its own, and its chunks name the open question they belong to in `of`.
xixo gathers the chunks in order into a temporary file and fails when the agent stops sending for a
minute or sends more than it said. Chunks are kept in whatever order they arrive, after the reply
too. A reply or chunk is taken only from the machine that was asked, and a chunk is taken only for a
`read` or a file. One question holds at most 256 files and 4 GiB, a machine holds at most 64 open
questions and 8 GiB received, and exchanges older than two hours are deleted by
`ForgetAgentExchangesJob`. A question asked inside a database transaction, as analysis asks, is
written and awaited on a connection of its own, so the channel sees it at once.

A `filesystem` names one of the folders the agent said it shares. Attaching one the agent does
not share is refused, and a folder the agent stops sharing is unusable. Every path the agent lists
must be relative and stay inside the folder. The folders, and which of them are writable, are set
only by the machine's configuration, which xixo writes during an install and never changes over the
connection, and the agent refuses any path outside them.

A write is a `write {folder, path, upload, size, replace}` question. The agent fetches the upload
the way it fetches one to extract, writes it to a temporary file beside its target, syncs it, and
moves it into place. It creates folders on the way inside the shared folder only, and refuses a
read-only folder, a link anywhere on the path, a name a walk skips, and bytes that do not match the
size. It replaces an existing file only when xixo asks it to, which xixo does only for a path the
catalog already holds on that resource, so a file someone else put there is never overwritten.

### Tools a machine offers

A machine offers MCP clients the tools its agent's configuration names in `tools`, and no others.
The agent says which in `hello`, and xixo keeps only the names it knows. A client reaches them
through the `resource` tool at `/mcp`, as commands on the machine, and never through a port on the
machine: each call is a question on the connection the agent already holds open. The agent refuses
the verb of a tool its configuration leaves out, and xixo lists and accepts only the commands of the
tools the machine offers, so neither side can widen what the other allows. A machine whose
configuration names no tools answers `health` and `discover` alone.

| Tool | Command | Agent verb | Does |
| --- | --- | --- | --- |
| `browse` | `browse` | `browse` | Lists the shared folders, or up to 200 files in one, with a cursor to read on. |
| `search` | `search` | `find` | Matches the query against xixo's index of the machine's folders, then against the paths of its files, ignoring case. The walk stops after 100 matches, 20,000 files, or ten seconds. |
| `read` | `read` | `peek` | Sends up to 256 KiB of a file. |
| `write` | `write` | `place` | Writes a file of at most 1 MiB into a writable folder. |
| `extract` | `extract` | `examine` | Runs the machine's extractors on a file and answers with their steps, and none of the files they make. |
| `models` | `chat` | `model` | Asks a model server on the machine one question. |

The machine's other settings still apply. `read` sends bytes only from a machine whose configuration
sets `lend`; from any other machine, or one that is offline, it answers with the text and summary
analysis drew out of the file and says that the bytes stay on the machine. `write` reaches only the
folders the configuration marks writable, and xixo lists it only for a machine that has one. `chat`
is listed only for a machine that reported a model server. The agent sends the question to
`127.0.0.1` on the port it probed for that kind of server, Ollama on 11434 or LM Studio on 1234, as an
OpenAI-compatible chat completion. It takes no address, follows no redirect, and caps the prompt at
64 KiB, the answer at 64 KiB, and the time at 90 seconds.

Every command needs `xixo:resources:read`, and `write` also needs `xixo:resources:command`.
`browse`, `search`, `read`, and `extract` count as reading the catalog, so an agent run that has read
the web cannot use them. A folder attached as one person's `filesystem` resource, and a folder that
holds a file kept to one person, such as storage that holds someone's private upload, are out of
reach of every other person's token. xixo records each call as an audit event on
the `mcp` channel, with its arguments. The tools stop short of running anything on the machine: no
tool takes a command line, a program, or an address.

### The agent beside the server

Every install runs an agent beside the server, as the `xixo-agent` service of the example compose, and
it reads every file no machine's agent reads where it lies. It has no database and no keys, and sees
only its own state and the folders mounted into it. It enrolls itself through a directory
it shares with the worker, named by `XIXO_LOCAL_AGENT`: it leaves a `wanted` file, `EnrollLocalAgentJob`
leaves it a single-use enrollment token readable by its user alone, and it writes back the client it
enrolled as, which the job binds to the `local` machine, **This server**. It binds a client only
within twelve minutes of handing out a token, once for each token, and never one another machine is
enrolled as. A client named any other way is refused, and the reason shows on the machine's card.
Deleting the agent's state volume enrolls it again. The job reads nothing behind a link. See [extraction](/concepts/analysis/#extraction) for what it is asked.

## Health, internal stores, archiving, and deleting

A check calls the type's `check!` and records `checked_at` and `check_error`. A resource is healthy
when it has been checked and the last check raised no error. An `openai-compatible` resource with an
agent, embedding, or transcription model first asks only whether the server lists its models. If it
does, the check sets `probing_since` and hands the rest to a `CheckResourceJob`, which tries tool
calls, the context window, embeddings, and transcription. The resource reads as checking until that
job records its result, and keeps its last `checked_at` and `check_error` meanwhile. A probe that has
not finished in fifteen minutes stops reading as checking. `ScheduleChecksJob` runs every ten minutes. It
finds resources that were never checked, not checked in six hours, or failed a check more than ten
minutes ago, and checks each one in its own job, so a resource that stopped answering shows it before a sync or a tool call reaches it. It skips
a resource that is syncing, since the sync tests it better. Checking an MCP server asks it again for
its tools, so tools it adds or removes reach the proxy within six hours.

xixo keeps two stores for itself: `children`, for what is extracted from a file, and `derived`, for
previews, thumbnails, and the frames read from an animation or a video. Both are database resources, and neither is ever offered as a place for an
upload. Neither is listed or reachable by key through GraphQL or MCP. Neither can be archived,
synced, scheduled, or made a default, because xixo writes into them regardless of those settings.

Archiving sets `archived_at` and deletes nothing. An archived resource is left out of capability
queries, placement, the defaults, and the sync schedule. Restoring it clears the timestamp.

Only an archived resource can be deleted, so deleting always takes two steps. `deleteResource`
refuses a resource that is still in use, one with a sync or another run open, an internal store, and
a transport that another resource is still reached through, archived or not. A personal resource
can be deleted only by its owner, because `Resource.reachable_by` hides it from everyone else.

Deleting removes the resource's references, its runs, and its row, so its key is free to attach
again. Each feed that pointed into it is then handed to `ForgetPlacelessJob`, which forgets the
`xixo:file` feeds left with no originals, unless a note, a lifetime, or an edge someone made keeps
them (see [noticing what is gone](/concepts/references/#noticing-what-is-gone)), and reindexes the
rest. Forgetting a feed deletes the previews, thumbnails, and extracted children xixo stored for it
in its internal stores.

Deleting does not reach into the source, so the files in a bucket, a folder, or a mailbox stay
where they are. A `database` resource is the exception, because its files live in xixo's own
database, and they are deleted with it. A resource connected through masks keeps its connection in
masks until it is removed there. The deletion and each feed it forgets are recorded in the audit
log.
