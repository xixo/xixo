---
title: Tenants
description: How one xixo deployment serves one or more tenants, and how each tenant signs in through masks.
---

A tenant is a separate catalog with its own resources, feeds, analyses, runs, settings, and audit
trail. Every request and every job runs inside exactly one tenant.

## Resolving the tenant

A deployment declares its tenants in one of two ways. Setting both is an error.

| | Declared by | A request resolves by |
| --- | --- | --- |
| Single | `XIXO_TENANT=xixo` | Nothing. Every host is that tenant. |
| Multi | `XIXO_TENANTS=demo,acme` | The first label of the host name. `demo.xixo.example` is `demo`. |

The container entrypoint creates the declared tenants on boot. A host that names no tenant gets
`404 Unknown tenant`. The health check at `/up` is the only path served outside a tenant. See
[tenants and hosts](/guides/self-hosting/#tenants-and-hosts).

## Isolation

Isolation has two layers:

| Layer | What it does |
| --- | --- |
| Default scope | Every tenant model is scoped to the current tenant, and new rows take its id. |
| Row-level security | Every tenant table has `FORCE ROW LEVEL SECURITY` and a `tenant_isolation` policy. |

The policy compares each row's `tenant_id` with the tenant the database session is in, for reads and
writes. Outside a tenant the policy matches no rows, so code that skips the default scope still
finds nothing from another tenant. Active Storage's tables carry the same policy, so a signed blob
id from one tenant finds no row in another.

A Postgres role with `SUPERUSER` or `BYPASSRLS` ignores every policy. xixo checks its role the first
time a process enters a tenant, and raises an error if the role can bypass the policies. See
[the database role](/guides/self-hosting/#the-database-role).

Every job records the tenant it was enqueued in and runs inside it. A job enqueued outside a tenant
raises an error. All tenants share one OpenSearch index, and each searches through a filtered alias
of its own. See [search](/concepts/search/#tenants).

## Settings

A setting is a named value from a fixed list of choices. The browser app shows them under
**Settings**, then **Account**. A setting that was never changed reads as its default.

| Level | Belongs to | Read with | Changed with |
| --- | --- | --- | --- |
| `personal` | the person signed in | `xixo:settings:read` | `xixo:settings:write` |
| `shared` | everyone in the tenant | `xixo:settings:read` | `xixo:settings:write` |

The personal settings, such as **How the catalog opens**, change only how the browser app looks. The
shared settings decide how [analysis](/concepts/analysis/#extraction) renders images:

| Setting | Choices | Default |
| --- | --- | --- |
| **Thumbnail width** | 160, 240, 320, 480, or 640 pixels | 320 |
| **Hi-res size** | 1024, 1500, 2048, or 3072 pixels on the longest edge | 1500 |
| **Most frames read from an animation** | 1, 2, 4, 6, 8, or 12 | 4 |
| **Share of an animation's frames read** | 10, 25, 50, or 100 percent | 100 |

The hi-res image is what a thumbnail opens and what the vision model reads. A page capture keeps its
full length at the hi-res width. An item rendered before a change keeps its old images until it is
analyzed again.

The vision model is shown the share of an animation's frames, rounded up and never more than the
most frames read. At the defaults, an animation of up to four frames is read in full, and a longer
one is read at four frames spread evenly across it.

The `settings` query lists every setting the token may read, with its value, default, and choices.
`setSetting` changes one and refuses a value outside the choices. See the
[GraphQL reference](/reference/graphql/).

## Signing in

Each xixo tenant is a client of a masks tenant with the same name. By default xixo serves masks
itself at `/id` on each tenant's origin, so `demo.xixo.example` signs in at `demo.xixo.example/id`.
The built-in masks runs in xixo's processes, with its own database, session cookie, and keys.
`MASKS_ISSUER_TEMPLATE` names a masks server run apart from xixo instead, with `%{subdomain}` taken
from the request's host.

A new tenant has no client. Connecting one starts a handshake at `/auth/handshake`:

1. xixo sends the browser to masks with its name, its resource URL, its redirect URIs, and the
   scopes it uses.
2. A masks account that may approve connections approves the request.
3. masks returns a one-time initial access token, and xixo redeems it at masks' registration
   endpoint, server to server.

xixo stores the client's id and secret and its registration token on the tenant, with the secret and
the token encrypted. Disconnecting deletes the registration in masks.

`GET /auth/session` returns the signed-in account, or a `401` whose `error` is `handshake_required`
or `login_required`, which tells the browser which button to show. Signing in asks for every `xixo:`
scope except `xixo:settings:admin`. `/auth?privilege=admin` signs in again asking for that scope
too, and masks grants it only to a person whose scopes in masks cover it. See [who changes a
resource](/concepts/resources/#who-changes-a-resource) and the [scopes
reference](/reference/scopes/).

`/graphql`, `/mcp`, and `/uploads` all verify a masks access token. The browser's token comes from
its session, and other clients send `Authorization: Bearer`. A token is accepted only when:

- it was issued by this tenant's issuer,
- its audience is this tenant's resource URL, the origin followed by `/mcp`, and
- any `tenant` claim it carries names this tenant.

A token whose `tenant` claim names `acme` is refused at `demo`. The browser's session asks for the
same audience, so one token works on every path.
